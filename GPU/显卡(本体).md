#GPU怎么分配任务
**GPU 自己不会"认任务"，它只听 CPU 通过驱动下命令**。
**所以分配是 CPU 侧发起、驱动中转、GPU 硬件执行的链式过程**

1. CPU 下发一个"kernel 启动"命令

> [!Kernel ]
>  1.在 GPU 语境下，就是 "一段在 GPU 上运行的小程序"
> 类似 "工序卡"比如：把螺丝拧到螺母上,只是每个人操作的对象不同
> 2.Kernel Launch = CPU 向 GPU 发出的一条指令："嘿，把我写的这段代码（kernel）拿去跑，按这个 grid/block 配置来。"
> 3.Grid = 那次 launch 里定义的工作总量和组织形式，即"总共要开多少个 block、每个 block 有多少 thread"
> 4(Kernel Launch 是一个"动作"（动词），Grid 是一个"结构"（名词）


你在 PyTorch 里跑 output = layer(input)，底层最终会触发一次 kernel launch——也就是"让 GPU 跑一段小程序（叫 kernel）来处理这批数据"。

launch 时要告诉 GPU 三件事：

grid 有多大（总共要多少 block）

block 有多大（每个 block 多少 thread）

kernel 用哪份参数（指针、常量之类的）

2. 驱动把 block 分配到 SM 上

GPU 内部有很多个 SM（[[流式多处理器]]，4090 有 128 个，H100 有 132 个）。分配逻辑很简单粗暴：

💡 grid 里的 block 被一个个扔给 SM，哪个 SM 有空就扔哪个，直到所有 block 都分完。一个 block 一旦分给某个 SM，就一辈子待在那，不会被挪走。

SM 内部再细拆：一个 SM 同时可以跑多个 block（看显存/寄存器够不够），每个 block 又被拆成 warp（32 线程一组），SM 里的 warp scheduler 按周期把 warp 扔给 CUDA Core 去算。

3. 一张图串起来

一次 kernel launch（一个"任务"） └─ grid（所有 block 的集合） ├─ block 0 → SM 3 ├─ block 1 → SM 7 ├─ block 2 → SM 3 （同一个 SM 可以接多个 block） └─ ... 每个 block 里 └─ warp 0 (thread 0~31) └─ warp scheduler 每周期挑一个 warp 喂给 CUDA Core 

线程和任务的关系

先把术语对齐：

词是什么任务（task）通常指一次 kernel launch，比如"算 1024×1024 的矩阵乘"grid这个任务拆成的 block 总集合block一组 thread，同一个 SM 内协作（可共享 shared memory）warp32 个 thread 绑死一组，必须同步走（SIMT）thread最小执行单元，对应一次"算一个元素" 

举个具体例子：向量加法 C[i] = A[i] + B[i]，长度 1M

你 launch 一个 kernel，grid 设 15625 个 block，每个 block 64 个 thread（15625×64=1M）

每个 thread 负责算一个 i：C[i] = A[i] + B[i]

每个 block（64 个 thread）里的兄弟可以共享一点数据（虽然向量加用不上，但卷积/规约会用）

每 32 个 thread 自动绑成 warp，这 32 个 thread 每一步执行的指令是一样的，只是操作的数据下标不同（SIMT = 单指令多线程）
