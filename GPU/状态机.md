**状态机（State Machine)** 是一种计算模型，它的核心思想是：**系统在任何时刻都处于有限个“状态”中的一个，并且只能在特定条件下切换到另一个状态**。

电灯只有两个状态：开 和 关

你不能从“开”直接切换到“开”，也不能从“关”直接切换到“关”

唯一的切换条件是：按下开关

当前状态（开/关）决定了你按下开关后会发生什么（关→开，开→关）

这就是一个最简单的**有限状态机**（Finite State Machine, FSM）。

---
#状态机的三个核心要素

状态（State）：系统当前所处的状况（比如 OpenGL 里“当前绑定了哪个纹理”、“当前启用了深度测试还是混合模式”）

转移（Transition）：从一个状态切换到另一个状态的条件（比如调用 glEnable(GL_DEPTH_TEST) 就是从“深度测试关”转到“深度测试开”**）

动作（Action）：进入某个状态时执行的操作（比如开启深度测试后，GPU 开始做 Z-buffer 比较）

---
#OpenGL为什么是状态机

OpenGL 本质上是一个**巨大的全局状态集合**。你调用的绝大多数函数不是在“执行一个操作”，而是在修改 OpenGL 内部的某个状态，然后**后续的绘图命令（glDrawArrays）会根据当前所有状态的组合来决定画出来什么**。

状态机在游戏开发里的另一个经典例子：角色动画

一个游戏角色的“行为”也可以建模成状态机：

idle（待机） / | \ 行走 奔跑 跳跃 \ | / attack（攻击） 

从 idle 可以走到 walk、run、jump、attack

从 jump 不能直接走到 attack（必须落地后才能攻击）

从 run 可以走到 jump，但不能直接从 run 走到 idle（必须先减速到 walk）

每个状态定义了角色能做什么动作、不能做什么动作——这就是状态机在逻辑层面的应用。

#状态机的优缺点

|                优点                 |            缺点             |
| :-------------------------------: | :-----------------------: |
|           逻辑清晰，容易理解和调试            | 调试状态多了会爆炸（十几个状态互相连，变成蜘蛛网） |
| 适合描述顺序性或条件驱动的行为不适合并发或连续变化（比如平滑过渡） |    不适合并发或连续变化（比如平滑过渡）     |
|      实现简单（switch-case 或表驱动）       |    扩展性差，加一个新状态可能要改很多地方    |

总结

状态机 = 一组有限的状态 + 一组明确的转移规则。你只需要知道“当前在哪个状态”，就能确定系统接下来能做什么、不能做什么。

OpenGL 是状态机，游戏角色的 AI 是状态机，电梯的控制逻辑是状态机，TCP 协议也是状态机——它是一种非常通用的思维方式。
